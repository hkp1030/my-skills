# Write Polished Docs

## Overview

토론과 검토 과정에서 나온 재료를 최종 독자가 읽을 수 있는 문서로 정리한다. 대화의 흔적을 보존하지 말고, 근거가 있는 사실과 결정된 내용을 문서 목적에 맞는 문장으로 다시 쓴다.

## 기본 흐름

1. 문서의 독자, 목적, 사용 위치를 먼저 확인한다.
2. 원문을 `사실`, `결정`, `근거`, `리뷰/토론 흔적`으로 나눈다.
3. `리뷰/토론 흔적`은 그대로 옮기지 말고, 필요한 정보만 문서 문장으로 바꾼다.
4. 남길 내용을 문서 목적에 맞는 순서로 재배치한다.
5. 마지막에 메타 표현과 임시 표현이 남았는지 한 번 더 훑는다.

## 리뷰 문장 처리

리뷰 문장은 문서 재료일 뿐이다. 다음 표현은 최종 문서에 넣지 않는다.

- "좋은 지적입니다", "맞습니다", "이전 답변에서", "토론 결과", "AI와 논의하면서"
- "리뷰어가 말한 것처럼", "사용자가 지적한 대로", "검토 의견에 따르면"
- "아마", "일단", "나중에 보면", "어색할 수 있음", "더 나을 듯"
- 질문·반박·정정 과정을 설명하는 문장
- 작성자의 의도나 대화 맥락을 해설하는 문장

리뷰 문장을 처리할 때는 아래처럼 바꾼다.

- "이 필드는 include가 아니라 expand가 맞습니다." → "중첩 객체 필드는 `expand`로 요청합니다."
- "serializer에서 필터링하면 책임이 흩어집니다." → "필터링은 ViewSet의 prefetch 단계에서 처리합니다."
- "이름이 좀 애매할 수 있어요." → "필드명은 응답 의미가 드러나도록 명시적으로 정합니다."

## 문장 원칙

- 최종 문서는 대화록이 아니라 결과물로 쓴다.
- 결정된 내용은 현재형 또는 명령형으로 쓴다.
- 요구사항은 관찰 가능한 동작으로 쓴다.
- 근거는 필요한 만큼만 남기고, 설득 과정은 줄인다.
- 독자가 실행할 수 없는 감상, 칭찬, 자기검열 문장은 제거한다.

## 중복 정리

같은 내용은 한 문서 안에서 한 번만 설명한다. 동일한 사실, 결정, 요구사항, 주의사항이 여러 섹션에 반복되면 가장 자연스러운 위치에 모으고 나머지는 제거하거나 짧게 참조한다.

- 요약은 본문을 그대로 반복하지 말고 핵심 결론만 다른 추상도로 압축한다.
- 배경, 결정, 구현, 검증에 같은 문장이 반복되면 각 섹션의 역할에 맞게 하나만 남긴다.
- 같은 항목이 표와 본문에 모두 필요하면 표에는 구조화된 값, 본문에는 해석이나 사용 기준만 둔다.
- 반복을 줄이기 위해 의미 없는 동의어 표현을 늘리지 않는다. 필요하면 한 문장을 더 명확하게 고친다.

## 구조 잡기

문서 유형이 정해져 있으면 기존 형식을 따른다. 형식이 없으면 아래 중 필요한 것만 사용한다.

- 요구사항 문서: `Purpose`, `Scope`, `Current Behavior`, `Required Behavior`, `Acceptance Criteria`
- 설계 문서: `Context`, `Decision`, `Data Flow`, `Interfaces`, `Edge Cases`, `Test Plan`
- 작업 정리: `Summary`, `Changes`, `Validation`, `Risks`, `Next Steps`
- 회의 메모: `Decisions`, `Action Items`, `References`

## 최종 점검

제출 전에 다음을 확인한다.

- AI, Codex, Claude Code, 리뷰, 토론, 답변, 위에서 말한 내용 같은 메타 단어가 남아 있지 않은지 확인한다.
- 문장이 "왜 그렇게 생각했는지"보다 "무엇을 해야 하는지"를 말하는지 확인한다.
- 원문 리뷰 문장이 그대로 복사된 부분이 없는지 확인한다.
- 같은 사실, 결정, 요구사항이 여러 곳에서 반복되지 않는지 확인한다.
- 코드값, API 필드명, UI 문구처럼 정확해야 하는 값은 임의로 번역하거나 꾸미지 않는다.
