# Write Focused Tests

테스트는 대상 모듈이 약속한 동작만 검증한다. 테스트 수를 늘리기보다, 실패했을 때 어떤 결함을 가리키는지 분명한 테스트만 남기는 데 집중한다.

## 기본 원칙

- 테스트 대상 모듈의 책임 범위를 벗어나지 않는다.
- 라이브러리와 프레임워크가 보장하는 동작은 테스트하지 않는다.
- 기존 테스트가 이미 검증하는 동작은 다시 테스트하지 않는다.
- 구현 세부가 아니라 밖에서 관찰 가능한 동작을 검증한다.
- 테스트 하나는 하나의 동작만 확인한다.

## 작성 흐름

1. 대상 모듈의 책임과 공개 인터페이스를 먼저 정한다.
2. 기존 테스트를 읽고 이미 검증된 동작과 사용 중인 픽스처를 파악한다.
3. 아직 검증되지 않은 동작에만 테스트를 추가한다.
4. 각 테스트가 실패했을 때 어느 모듈의 어떤 결함인지 한 문장으로 설명되는지 확인한다.

## 모듈 범위 지키기

- 의존하는 다른 모듈의 로직은 그 모듈의 테스트에 맡긴다. 여기서는 그 결과를 사용하는 방식만 검증한다.
- 다른 모듈의 결과가 필요하면 경계에서 대체하거나 최소한의 데이터만 준비하고, 그 모듈의 내부 동작을 단언하지 않는다.
- private 함수, 내부 호출 순서, 중간 상태는 검증 대상에서 제외한다.
- 여러 모듈을 거쳐야만 확인되는 동작은 통합 테스트로 분리하고 단위 테스트에 섞지 않는다.

## 라이브러리 동작 제외

아래는 프로젝트 코드가 아니라 라이브러리가 보장하는 동작이므로 테스트하지 않는다.

- ORM이 값을 저장·조회하고 기본값을 적용하는지
- 직렬화기가 선언된 필드를 출력하고 필수 필드 누락을 거부하는지
- 라우팅, 인증 미들웨어, 표준 라이브러리 함수의 기본 동작
- 설정값이 단순히 읽히는지

프로젝트가 그 위에 덧붙인 로직인 커스텀 검증, 조건 분기, 데이터 변환만 검증한다.

## 중복 테스트 방지

- 같은 분기를 입력값만 바꿔 여러 테스트로 늘리지 않는다. 경계값이 실제로 다른 경로를 타는 경우에만 추가한다.
- 상위 계층 테스트가 이미 지나가는 경로를 하위 계층에서 같은 단언으로 반복하지 않는다.
- 비슷한 케이스가 여럿이면 파라미터화로 묶는다.
- 새 테스트를 추가하기 전에 기존 테스트를 수정하거나 확장하는 편이 맞는지 먼저 본다.

## 최종 점검

- 이 테스트를 지우면 어떤 동작이 보호되지 않는지 설명할 수 있는가
- 라이브러리를 교체해도 테스트의 의미가 유지되는가
- 기존 테스트와 단언 내용이 겹치지 않는가
- 테스트 이름만 읽고 검증하는 동작을 알 수 있는가
